# RND: доставка профилей, массовый перенос, статистика и бэкап в Telegram

Статус: реализовано в ветке `feature/family-notifications`.

## Цели

Панель используется для семьи и друзей: большинство пользователей не
технические и получают VPN только через Telegram-бота. Сейчас администратор
вручную пересылает каждый новый или перенесённый конфиг, не видит, кто
перестал пользоваться VPN, а резервные копии лежат на том же сервере, что и
панель.

| # | Фича | Результат для администратора |
| --- | --- | --- |
| 1 | Доставка профиля пользователю | Созданный или перенесённый профиль сам приходит пользователю в бот. |
| 2 | Массовый перенос выбранных профилей | На странице сервера можно отметить несколько профилей и перенести их на другой VPS одной операцией. |
| 3 | Статистика и еженедельная сводка | Раз в неделю приходит сводка по трафику и «тихим» пользователям; пользователь видит свою статистику в боте. |
| 4 | Бэкап панели в Telegram | Снимок `panel.db` регулярно уходит администратору в Telegram, то есть хранится вне VPS. |

Не входит в объём: подписочные URL (`/sub/<token>`), автоматический выбор
резервного сервера, веб-интерфейс статистики для роли `user`.

## Ограничения текущей архитектуры

- Состояние хранится одним JSON-документом в SQLite (`storage.py`), поэтому
  новые поля добавляются в существующие объекты без миграций схемы.
  Отсутствующие поля трактуются как значения по умолчанию.
- Часть маршрутов синхронные (`def`), они выполняются в threadpool FastAPI и
  не могут вызвать `asyncio.create_task`. Тест
  `test_ssh_routes_stay_threadpool_handlers` требует, чтобы часть из них такими
  и оставалась.
- Бот работает как asyncio-задача с long polling. Отправка уведомлений из
  панели не должна от него зависеть: для отправки достаточно токена бота и
  прямого вызова Bot API, как уже сделано для системных тревог
  (`_send_telegram_message`).
- В `notifications.html` нет i18n (только русский), страница сервера
  локализована на 5 языков через `translations/*.json`.

## 1. Доставка профиля пользователю

### Когда отправляется

| Событие | Точка в коде | Тип сообщения |
| --- | --- | --- |
| Админ создал профиль и назначил его пользователю на странице сервера | `api_add_connection` | `created` |
| Админ создал или привязал профиль в карточке пользователя | `api_add_user_connection` | `created` / `assigned` |
| Админ создал пользователя вместе с профилем | `api_add_user` | `created` |
| Админ создал профиль в боте и выбрал владельца | `telegram_bot._admin_create_client` | `created` |
| Одиночный перенос профиля | `api_transfer_connection` | `transferred` |
| Массовый перенос | `api_transfer_connections_bulk` | `transferred` |

Профили, созданные самим пользователем через self-service, не отправляются
повторно: он уже получил конфиг в ответе.

### Условия отправки

Сообщение уходит, только если одновременно:

1. включена глобальная настройка `settings.user_notifications.enabled`
   (по умолчанию включена) и настройка конкретного события
   (`on_create` / `on_transfer`);
2. в запросе не передано `notify_user: false` (галочка в модальном окне);
3. у владельца профиля есть `telegramId`, пользователь включён;
4. задан токен бота.

Если в боте профиль создаёт сам админ для себя (владелец = отправитель), бот
не дублирует сообщение: конфиг уже показан в этом же чате.

### Содержимое

Первое сообщение объясняет причину («Администратор выдал вам новый профиль» /
«Ваш профиль перенесён на новый сервер, старая конфигурация больше не
работает»). Дальше конфиг в том же формате, что и по кнопке в боте: ссылка
для Xray/Telemt; для WireGuard-семейства текст, `vpn://`-ссылка и `.conf`-файл.
Если конфиг получить не удалось, приходит подсказка открыть `/connections`.

Язык берётся из `user.telegram_lang`. Он сохраняется при привязке аккаунта
по приглашению, иначе используется `ru`.

### Реализация

- `user_notifications.py` — чистая логика: настройки по умолчанию, решение
  «отправлять ли» (`resolve_recipient`), планирование отправки из
  синхронного и асинхронного кода (`schedule`).
- `telegram_bot.send_profile_notification(...)` — отправка через временный
  `httpx.AsyncClient` с переиспользованием `_send_config_text`.
- Планирование: при старте панель запоминает event loop. Из синхронного
  маршрута корутина ставится через `asyncio.run_coroutine_threadsafe`, из
  асинхронного — через `create_task`. Маршрут не ждёт Telegram, поэтому
  создание профиля не замедляется.
- Ответ API содержит `user_notification`: `queued`, `disabled`, `no_telegram`,
  `no_user`, `no_bot`. По нему UI показывает toast.
- Ошибки доставки (пользователь заблокировал бота и т. п.) логируются и
  записываются в `user_notifications.last_error`. Проверяется ответ Telegram
  на каждую часть (вступление, конфиг, ссылка, файл), а не только на первое
  сообщение.

## 2. Массовый перенос выбранных профилей

### API

`POST /api/servers/{server_id}/connections/transfer-bulk`

```json
{ "protocol": "awg2", "client_ids": ["..."], "target_server_id": 1, "notify_users": true }
```

Ответ:

```json
{
  "status": "success | partial | error",
  "transferred": 3,
  "failed": 1,
  "results": [
    { "client_id": "...", "name": "Мама", "status": "success", "new_client_id": "...", "user_notification": "queued" },
    { "client_id": "...", "name": "Гость", "status": "error", "error": "..." }
  ]
}
```

### Алгоритм

1. Проверки: те же, что и для одиночного переноса, плюс от 1 до 100
   уникальных `client_ids`.
2. Открывается по одному SSH-соединению к источнику и цели; списки клиентов
   читаются один раз.
3. Каждый профиль переносится общей функцией `_transfer_client_between`
   (выделена из одиночного переноса): создать на цели → сохранить disabled →
   удалить на источнике → при ошибке откатить цель. Семантика «сначала
   создаём, потом удаляем» сохраняется для каждого профиля.
4. Ошибка одного профиля не прерывает остальные. Состояние сохраняется после
   каждого успешного переноса, поэтому частичный результат не теряется при
   падении процесса.
5. Блокировки: переносы сериализуются отдельным `TRANSFER_LOCK`, а общий
   `DATA_LOCK` берётся только на короткое «загрузить → изменить → сохранить»
   после каждого профиля (`_commit_transfer`). SSH-операции идут без
   `DATA_LOCK`, поэтому медленный VPS не блокирует остальную панель. Так как
   индексы серверов могут сдвинуться во время переноса (сортировка,
   удаление), связи обновляются через стабильные `uid` серверов.
5. После завершения каждому пользователю с Telegram уходит его новый конфиг.
6. В аудит пишется `connection_transferred` на каждый профиль и
   `connections_bulk_transferred` на всю операцию.

### UI

На странице сервера у каждого профиля появляется чекбокс. Когда что-то
выбрано, над списком появляется панель: «Выбрано: N · Выбрать все · Снять ·
⇄ Перенести выбранные». Выбор хранится в `Set` и переживает 5-секундный
автоповтор отрисовки; при смене протокола он сбрасывается. Модальное окно
показывает выбранные профили, целевой VPS, галочку «Отправить новые профили
пользователям в Telegram», а после выполнения — построчный результат.

## 3. Статистика и еженедельная сводка

### Сбор данных

Фоновая синхронизация трафика (раз в 10 минут) уже считает приращение байтов
по каждому профилю. Для каждого профиля с приращением больше 0 функция
`activity_stats.record_traffic` дополнительно:

- ставит `user_connection.last_active_at` и `user.last_active_at`;
- ведёт месячный счётчик `user.traffic_month` с ключом
  `user.traffic_month_key` (`YYYY-MM`), который обнуляется при смене месяца.

Активность считается по трафику, а не по handshake: это работает для всех
протоколов одинаково и не требует разбора форматов времени.

### Сводка администратору

Настройки `settings.weekly_digest`: включена, Chat ID (по умолчанию —
чат системных тревог), день недели, час, часовой пояс, порог неактивности
в днях (по умолчанию 7). Состояние (`data.digest_state`) хранит время
последней отправки и базу `traffic_total` по пользователям для расчёта
недельной разницы.

Текст сводки:

```
📊 Сводка VPN за неделю (18.09–25.09)
Всего трафика: 42.1 GB · активных: 5 из 7

👤 Мама — 12.3 GB · сегодня
👤 Папа — 1.2 GB · 2 дн. назад

😴 Не пользовались 7+ дней:
• Бабушка — 12 дн. назад
• Гость — нет данных

⛔ Отключены: Старый ноутбук
```

В сводку попадают пользователи, у которых есть хотя бы один профиль.
Проверка «пора ли отправлять» выполняется в цикле планировщика уведомлений
(раз в 20 секунд): день и час совпали, а в этот локальный день сводка ещё не
уходила. Кнопка «Отправить сейчас» отправляет сводку без сдвига базы, чтобы
тестовая отправка не портила недельный расчёт.

### Статистика пользователю в боте

Кнопка «📊 Моя статистика» в меню пользователя: трафик за текущий месяц,
всего, лимит и остаток (если задан), срок действия, последняя активность по
каждому профилю.

## 4. Бэкап панели в Telegram

Настройки `settings.telegram_backup`: включён, Chat ID, интервал (1 или
7 дней), а также `last_sent_at`, `last_status`, `last_error`.

- Снимок берётся тем же `STATE_STORE.export_database()`, что и ручная выгрузка
  в Settings, и отправляется `sendDocument` как
  `amnezia-panel-YYYYMMDD-HHMM.db` с подписью: число серверов, пользователей
  и профилей, отпечаток мастер-ключа.
- Если `PANEL_MASTER_KEY` не задан, включить отправку нельзя: в файле были бы
  открытые SSH-пароли и ключи. API возвращает 400, UI показывает
  предупреждение.
- Наличие ключа ещё не гарантирует, что база зашифрована: база, созданная до
  появления ключа, хранит старые значения открытыми. Перед отправкой
  хранилище проверяет payload на открытые секретные поля
  (`plaintext_secret_paths`), при необходимости перешифровывает его
  (`reseal`) и отказывается отправлять, если открытые поля остались.
- Копия для Telegram собирается с `VACUUM`, чтобы свободные страницы SQLite
  со старыми версиями payload не попали в файл.
- Лимит Telegram на документ — 50 МБ; при превышении отправка не выполняется,
  ошибка сохраняется в `last_error`.
- Кнопка «Отправить сейчас» для проверки.
- Восстановление — существующим механизмом Settings → Restore с тем же
  мастер-ключом.

## Настройки и API

Все новые настройки находятся на странице «Уведомления» в отдельных карточках
в текущем стиле.

| Метод | Путь | Назначение |
| --- | --- | --- |
| GET | `/api/notifications/family` | Текущие настройки трёх блоков и статус (мастер-ключ, токен бота, последняя отправка). |
| POST | `/api/notifications/user-profiles` | Настройки доставки профилей. |
| POST | `/api/notifications/digest` | Настройки сводки. |
| POST | `/api/notifications/digest/send` | Отправить сводку сейчас. |
| POST | `/api/notifications/telegram-backup` | Настройки бэкапа. |
| POST | `/api/notifications/telegram-backup/send` | Отправить бэкап сейчас. |
| POST | `/api/servers/{id}/connections/transfer-bulk` | Массовый перенос. |

## Безопасность

- Конфиг уходит только на `telegramId` владельца профиля. Этот ID
  привязывается через одноразовое приглашение или вручную администратором.
- Сводка и бэкап отправляются только в явно указанный администратором чат.
- Бэкап без мастер-ключа запрещён.
- В аудит и логи не пишутся конфиги, токены и содержимое бэкапа.

## Тестирование

- Юнит-тесты для `user_notifications` (решение и планирование),
  `activity_stats` (месячный счётчик, активность, текст сводки, расчёт «пора
  ли»), расписания бэкапа.
- Тесты маршрутов с моками SSH: массовый перенос (успех, частичный отказ,
  откат), постановка уведомлений при создании и переносе.
- Тест бота: кнопка статистики и её обработчик.
- Существующий набор тестов, включая проверку JS на всех локалях, должен
  оставаться зелёным.
